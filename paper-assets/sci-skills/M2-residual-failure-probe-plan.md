# M2 剩余失败诊断计划

日期：2026-10-07。探索性本地机制诊断，非正式论文效果实验；不改变产品代码或原知识库，不调用远程模型。

研究问题：在本项目真实代码历史和原文模块中，版本选择、前置模块保持、来源定位的失败是否超出简单规则可解决的范围？

输入：Knowledge Manager 的 Git 历史、当前工作目录 Python 源码、已保存的单节点部署文档及其抽取模块。当前工作目录有未提交修改，因此与 Git HEAD 区分，并保存输入快照与 SHA-256。

三个诊断：

1. 历史版本：纳入所有修改 storage.py 的主线提交，提取实际 search_modules 函数及版本存在关系。明确指定目标提交和符号；比较混合版本 BM25、仅最新版本、目标版本过滤后 BM25。正确标签为目标提交中的函数哈希，不是人工答案标签，也不是代码任务执行成功。
2. 配套模块：仅使用部署文档现有抽取模块，在隔离知识库配置“operations 必带 Prerequisites”。查询固定为 `single-node-deploy install`、`systemctl install`、`install service deployment`；数量上限为 1、2、3、6。执行真实 search_modules，对照“先保留已声明的必带项，再截断”的简单规则。上限 1 不可能容纳两个独立模块，应拒绝输出不完整组；不以突破上限作为成功。依赖规则由本次分析显式设置，不能称为从真实用户日志发现的自然任务依赖。
3. 来源跨度：以真实完整部署文档封装本地页面对象，对原文模块执行真实 _stamp_module；核查跨度是否完整包含相应原文片段，对照确定性 exact-substring 定位。检查的是逐字完整包含，不是自动语义蕴含判断。页面对象为受控输入，没有真实连接 Confluence。

分析单位：一个仓库、一个文档及其版本/查询条件。同一函数的版本、同一查询不同上限不是独立样本；只报告逐条件结果和描述计数，不做 p 值、置信区间或总体优越性推断。没有训练/测试分割，这些输入只能用作开发诊断。

软件：现有本地 Python；版本文本来自 git show，快照不切换工作目录。缺失历史函数明确排除并记录。参数 BM25 k1=1.2、b=0.75，词法切分；按实际模块数量而非读者 token 预算。真实 Agent、密集/神经重排、Hyper-RAG/CUPMem 等强方法效果未在本轮复现。

可证伪准则：若失败均可由已知版本元数据过滤、声明依赖优先保留、精确跨度定位解决，当前结果不能支撑独立方法创新；只有找到更强现有方案也持续失败的真实任务，才考虑进入方法设计。

输出：输入快照、脚本、逐条件结果、环境/哈希记录、执行日志和中文判断。执行前状态：NOT_EXECUTED。
