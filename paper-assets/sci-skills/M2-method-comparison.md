# 现有方法对比、候选改进方向与实验对照

核对日期：2026-10-07。来源深度和定位详见 `M2-literature-verified-20261007.json`。
这是针对当前选题的有限文献分析，不是系统综述，不证明不存在其他相似方法。

## 现有方法对比表

| 文献/路线 | 已核实的机制 | 使用条件与成本 | 本次评价中的位置 |
|---|---|---|---|
| A-Mem [L1] | 结构化记忆、LLM关联与演化；保留原始交互内容 | 生成模型与编码器；长对话记忆任务 | 最近邻组织路线；未复现，不能宣称首次模块化或首次关联 |
| RAPTOR [L2] | 聚类/摘要树；原始叶节点与多层检索 | 编码器、聚类、生成式摘要；长文档问答 | 多粒度比较依据；未复现，不用轻量树近似冒充原版 |
| ReadAgent [L3] | 分页、gist与按需回读原文 | 生成模型参与；长文档阅读 | 按需回读先例；只核对出版页摘要，未全文精读 |
| MAGMA [L4] | 多关系图、策略检索、来源标识和显著性预算 | 图构建与异步LLM推断；长对话任务 | 最重要竞争路线之一；未复现，不主张首次来源追踪或预算控制 |
| DocPrompting [L5] | 检索文档后生成代码 | 需要下游代码生成与执行评估 | 软件任务参考；只核对摘要与出版记录 |
| BEIR [L6] | 在异质检索任务上评估多类检索器 | 不同架构成本不同；摘要支持BM25作为强基线 | 对照合理性参考；不能拿本文案例当BEIR或跨域验证 |

上述论文报告的性能不进入本项目结果表。方法间条件不同，没有据此给出排名、成本数字或普遍优劣结论。

## 不足分析

外部不足不能用“摘要未提及某功能”推断。A-Mem保留原始内容；RAPTOR含原始叶节点；ReadAgent回读原文；MAGMA含来源标识与预算。因此，模块化、原文保留、关联、追溯和预算都不是当前已成立的独占创新。

已观察到的项目内问题更具体：

1. `storage.search_modules` 按模块数量截取，并可在其后添加关联/配套模块；接口没有token预算参数。固定top-k并不构成等token比较，需要独立记录实际加载内容。
2. 现有候选评测把模块文本交给脚本内BM25，并不等于调用当前KM检索实现。它适合作粒度对照。
3. 首版183个模块均为自动抽取草稿；关联只是同源邻接，不能视为专家语义边。当前也没有审核前后对照，不能声称人工审核提高准确率。

## 改进方向（研究假设）

研究对象收敛为软件工程项目文档/源码知识库。以共同的原文证据位置为评价基准，检验模块组织和受控关联在固定上下文预算下是否增加必要证据覆盖，并完整报告代价与失败。

候选设计：检索候选 -> 合并重叠原文区间 -> 估计包括来源标记在内的token成本 -> 在预算内打包 -> 保存加载清单和源映射。此设计尚未实现或证明新颖性。

它的潜在价值是可复现案例和可审查评价协议。若声称算法贡献，还需提出有实质区别的机制，并用强对照与消融证明；仅实现这些已有组件不够。

保留当前工作题目，同时记录一个更保守的备选：
《固定上下文预算下可追溯知识模块检索的设计与案例评估》。

## 正式对照方法（协议草案，未运行）

| 组别 | 输入与检索 | 用途 |
|---|---|---|
| B1 原文chunk BM25 | 同一组冻结原文；统一分词与BM25参数 | 端到端词法对照 |
| B2 边界感知chunk BM25 | 相同原文；尊重段落/代码边界 | 避免只与粗糙切块比较 |
| B3 模块BM25 | 抽取模块正文；与B1/B2用相同排序器 | 隔离组织粒度的贡献 |
| S0 实际KM | 调用锁定版本的实际检索链路；不以B3替代 | 当前系统基线 |
| S1 KM+预算打包 | S0候选加源区间去重与明确预算 | 待实现的候选方案 |
| 消融 | S1关闭关联、关闭去重等 | 识别独立影响；不预设结果 |

Dense/hybrid为强对照候选：软件包存在，但本地模型权重与离线可运行性未核实，不能声称已具备可执行复现。缺少该强对照时，结论只能限定于已测试的词法/本地路线。
A-Mem、RAPTOR、MAGMA、ReadAgent为相关工作，尚非已实现实验组；轻量近似必须另命名，不能报告为原版复现。

## 验证约束与评价目标

- 每组使用同一冻结原文、相同任务、同一tokenizer和预算规则；按实际送入下游的文本计成本。索引、候选摘要与工具返回内容分别记账，不能隐藏前置上下文。
- 预算暂定512/1024/2048/4096 tokens用于敏感性分析，最终协议在查看主结果前冻结。未执行token测量；安装了tokenizer包不等于权重可离线使用。
- 使用原文证据单元，而不是模块ID，评估必要步骤/条件的覆盖；同一证据出现多次只计一次。部分跨度覆盖如何计分须预先规定。
- RQ1：相同预算下必要证据覆盖与来源映射是否改善？RQ2：粒度、关联和打包分别贡献什么？RQ3：收益是否随预算与任务改变？
- 任务覆盖事实、流程/约束、跨段依赖、故障定位与库外需求。不能仅把模块标题改成问题。开发/测试任务按源文件或业务流程分组，减少同源泄漏；仅10份原文件限制统计外推。
- AI生成的任务和标签明确标为自动/银标签。若无独立人工核验，只报告受控自动任务案例，不能改称人工黄金标注或真实用户评测。
- 目前没有可调用本地生成模型的证据；不安排远程API作为必要步骤。没有真实下游输出时，只评估检索/上下文证据，不虚构答案正确率。
- 记录加载token、源证据覆盖、来源匹配、冗余与时延；传统排序指标仅作辅助。无任务标签时，不生成MRR/nDCG主结果。
- 审核质量收益目前没有实验依据。后续只有实际审核过程、修改与时间记录存在，才能评估人工审核成本和效果。
