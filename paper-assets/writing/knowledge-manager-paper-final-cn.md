# Knowledge Manager 中文投稿型终稿

> 说明：本稿基于 `knowledge-manager-paper-v3.md` 与 `knowledge-manager-finalization-plan.md` 重构，定位为“北大核心及同类较强期刊/稳妥路线”的应用型系统论文工作稿。正文按用户指定写作顺序组织，投稿排版时可再调整为“摘要-引言-相关工作-系统设计-实现-评估-结果-讨论-结论”的常规顺序。

## A. 一句话核心论点

在小中型团队知识库的 AI 协作开发场景中，本文通过 Knowledge Manager 所采用的结构化知识模块、`extract-review-approve` 人工审核流程、Git 原生 JSON 存储与 MCP 按需加载机制，实现了更清晰的知识边界表达、更可审查的知识治理路径和更可控的运行时加载方式，证据来自 MCP 协议测试 `14/14` 通过、`2026-06-13` release gate 在 `xs/s/m` 三档均为 `ready_for_production=true`、搜索路径时延记录、OAuth 知识库 5 个受控路由场景中 4 个模块选择正确，以及评测代码已支持 rank-based 与 failure-based 指标，其适用边界是当前证据主要覆盖读路径、搜索路径与协议路径，尚不能外推到所有 chunk-based RAG、`l/xl` 规模、充分验证的长文档处理、完整写路径或真实会话中的全自动路由。

## E. 正文初稿

### 1. 系统设计

Knowledge Manager 的设计对象是小中型团队知识库。这里的“知识库”不是开放域网页语料，也不是已经具备完整数据治理流程的大型企业平台，而是开发团队在日常协作中积累的架构说明、接口约束、部署经验、排障步骤和项目约定。这类知识通常规模不大，却经常被开发者和 AI 协作工具反复读取。系统设计首先要解决的不是“大规模召回”问题，而是知识进入系统后能否被审核、能否保留边界、能否在运行时按任务加载。

纯切块检索在知识接入上有明显优势。把文档切成 chunk 后建立索引，能够较快接入现有检索流程，也能复用 BM25、向量检索或混合检索等成熟方法。本文不把这种路线写成低质量方案。问题在于，在小中型团队知识库中，一个命中的 chunk 未必能说明它属于哪个知识边界、是否经过团队确认、是否仍适用于当前版本，或者是否遗漏了 caveat。这个问题在 AI 协作开发中更敏感，因为被加载进上下文的内容可能直接影响代码修改、排障建议或架构判断。

Knowledge Manager 采用结构化知识模块作为基本组织单元。模块包含 `overview`、`details`、`examples`、`references` 和 `caveats` 等字段，使“这条知识讲什么、怎么使用、从哪里来、有什么限制”被放在同一个对象中。这样做不是为了让数据结构看起来整齐，而是为了让人和模型在读取前就能看到知识边界。尤其是 `caveats` 字段，它承担了防止知识被过度泛化的作用。

Knowledge Manager 保留人工审核是一个有意的工程取舍。系统不把抽取结果直接写入正式库，而是先进入 `.staging/`，再由人工 review 和 approve。这个流程会增加入库成本，但它给团队留下了确认适用条件、补充 caveat、删除过期实践和修正模块边界的机会。对于团队内部知识，这一步不是可有可无的“人工润色”，而是知识能否被后续代理直接引用的责任边界。

Git 原生 JSON 存储使知识治理接近代码治理。approved module 以 JSON 文件存在，索引由 `index.json` 维护，知识变更可以通过 Git diff、review 和 version 追踪。团队可以看到某次提交删除了哪个 caveat，新增了哪些 examples，或者把哪个模块移动到新的分类下。这个设计本身不构成理论创新，但它适合小中型团队已有的协作习惯，也减少了引入专用知识平台的维护负担。

MCP 按需加载把知识访问拆成“发现”和“读取”两个阶段。客户端可以先读取 `knowledge://index` 或分类信息，再通过 `search_modules` 查找相关模块，最后用 `load_module` 加载少量模块。与整库注入相比，这种路径更容易控制上下文规模，也更容易分析哪些模块被实际使用。它并不自动保证回答质量，但为后续的路由评估和知识治理留下了接口基础。

### 2. 实现细节

Knowledge Manager 的知识流转路径从原始文本开始。系统读取原始文档后，由 extractor 生成候选结构化模块，候选结果先写入 `.staging/`，审核通过后再进入正式分类目录并更新 `index.json`。这一实现路径对应 `extract -> review -> approve -> serve`，也对应本文主张中的“先抽取、再治理、再服务”。

模块存储保持在文件系统层面。正式模块按类别存放，索引文件用于 CLI 与 MCP 侧发现模块。维护者可以直接打开 JSON 文件检查内容，也可以在 Git 中查看变更。这种透明性对小中型团队很实际，因为很多团队更愿意复用已有代码审查流程，而不是再维护一套黑箱知识平台。

Extractor 对长文本做了分块处理。当前实现通过 `_chunk_text()` 将输入拆成多个片段，并由 `_effective_chunk_size()` 将实际 chunk 大小限制在 `4000` 字符以内。抽取日志记录 chunk 数、chunk size 和 overlap 等信息。这个设计说明系统已经意识到长输入一次性送入模型会带来稳定性风险。

跨块去重用于降低重复模块进入知识库的概率。系统在遍历 chunk 抽取结果时维护 `seen_ids` 集合，如果不同 chunk 生成相同 module ID，就跳过重复项。这个机制不能证明长文档抽取完整，但能处理长文档分块后常见的重复生成问题。

JSON retry 用于处理模型输出格式不稳定。若模型返回内容不能解析为 JSON 数组，系统会把错误信息写回提示并要求重新输出 JSON 数组；若返回 JSON 对象而不是数组，也会触发重试。这个实现细节很重要，因为它说明系统没有把 LLM 输出当作天然可靠的结构化数据，而是设置了格式恢复路径。

抽取提示词要求保留源文本原语言。对中文团队文档或中英文混合文档来说，强制翻译或统一改写可能丢失项目语境。当前实现至少在提示层面保留原语言，这有利于团队成员在审核阶段判断模块是否贴合原文。

CLI 与 MCP 服务同一套模块和索引。CLI 提供 `init`、`list`、`search`、`show`、`review`、`serve` 等人工维护命令；MCP 侧提供索引资源、模块搜索、模块加载和分类访问。两条接口面向不同使用者，但不形成两套知识副本，这降低了维护不一致的风险。

### 3. 实验设置

当前验证分为工程验证、探索性路由验证和评测框架能力验证。工程验证回答系统是否能通过 MCP 协议路径和 release gate；路由验证回答结构化索引是否能在小样本场景中帮助选择模块；评测框架能力验证回答项目是否具备进一步做 judged baseline 对比的基础。这样的划分避免把现有材料包装成完整 benchmark。

MCP 协议测试覆盖 14 个协议路径。测试包括初始化握手、资源列表、索引读取、工具列表、模块搜索、模块加载、分类列表和错误处理。该测试使用真实 OAuth 知识库，报告中总测试数为 `14`，通过数为 `14`。

发布门禁使用 `2026-06-13` 的 `xs/s/m` 三档结果。三档 release verdict 均为 `ready_for_production=true`，并记录了 `search_http` 与 `mcp_search_modules` 的 mean 和 p95 时延。本文将这些结果解释为设定规模下的服务化可运行性证据，而不是大规模生产证明。

路由行为测试使用 OAuth 知识库中的 5 个受控场景。测试关注模型读取索引后是否选择正确模块、是否出现无关模块过载，以及是否能识别知识边界。当前结果显示 5 个场景中 4 个模块选择正确，并且未观察到明显 irrelevant over-loading。

评测框架已支持多种排序与失败分解指标。项目代码支持 `first-hit rank`、MRR、nDCG@k、recall@k、baseline win rate、false-positive / false-negative rate、policy failure rate 和 retrieval failure rate 等字段。本文只把这一点写作“评测能力已具备”，不把它写成“主实验已经完成”。

严格的 baseline 对比仍是缺口。[证据不足：当前材料缺少至少 2 类真实语料、30-50 个 judged queries、BM25/关键词 chunk baseline 与 chunk-only retrieval baseline 的统一对比结果。] 因此，本文的实验设置部分只能给出对照评估协议，不能声称已经完成多语料检索比较。

### 4. 结果分析

MCP 协议测试表明系统接口链路已经跑通。`test-results/mcp-protocol.md` 记录 `14/14` 通过，覆盖握手、资源读取、工具调用和错误处理。这一结果支持“Knowledge Manager 已具备可接入 MCP 服务路径”的结论。它不能说明结构化模块优于 chunk-only retrieval。

发布门禁结果说明系统在 `xs/s/m` 三档设定规模下满足项目门槛。`search_http` 在 `xs`、`s`、`m` 三档的 mean / p95 分别为 `207.113 / 220.442 ms`、`370.877 / 380.882 ms`、`404.838 / 414.091 ms`；`mcp_search_modules` 分别为 `208.454 / 230.392 ms`、`476.714 / 486.724 ms`、`593.720 / 625.424 ms`。这些数字可以进入结果表，但不应被解释为 `l/xl` 规模或复杂生产环境的证据。

路由测试显示结构化索引在小样本场景下有用。OAuth 知识库 5 个场景中有 4 个完成正确模块选择，且未观察到明显无关过载。这个结果与模块标题、摘要和标签提供索引线索的设计一致。由于场景数只有 5 个，本文只能写“受控场景中观察到可用的模块选择行为”。

路由测试也暴露了知识边界问题。在 “OAuth 和 JWT 有什么区别？” 场景中，知识库覆盖 OAuth 但不覆盖 JWT，模型可能加载 OAuth 模块并依赖自身常识补全 JWT 对比，而不是明确提示 JWT 超出知识库范围。这个失败说明系统需要更明确的 scope、coverage 或拒答信号。

troubleshooting 查询暴露了模块摘要和 caveat 的不足。在 “如何调试 OAuth 重定向问题？” 场景中，模型能加载 redirect 相关模块，但模块摘要更偏“机制说明”，没有突出 debugging 信号；部分 `caveats` 字段为空。这个结果提示系统对“怎么工作”的支持强于“出了问题怎么查”。

短词检索失败说明当前匹配机制仍有脆弱点。`retrieval-accuracy.md` 记录 `auth` 查询返回空结果，即使相关模块都属于 auth 类别。这个失败不能被归为偶然噪声，因为短词、缩写和类别名在团队知识库检索中很常见。后续 judged query 集应把这类查询单独标记。

评测框架能力为正式实验提供了基础。项目已支持 first-hit rank、MRR、nDCG@k、recall@k、baseline win rate 和失败类型字段。这个结果说明项目不再只停留在 hit/miss 演示上。问题在于，指标实现不等于指标结果，主实验仍需要真实语料和统一 baseline。

当前结果最稳的解释是工程适配性。结构化模块、人工审核、Git 存储和 MCP 按需加载共同支持一个可审查、可追踪、可按任务读取的知识使用路径。这个结论比“检索性能全面更好”窄，但与现有证据更一致。

### 5. 失败案例与局限性

知识边界识别不足是当前最明确的失败类型。OAuth/JWT 场景说明，当用户问题部分落在知识库之外时，系统缺少足够强的 out-of-scope 信号。对于团队知识库，这种失败比普通检索遗漏更危险，因为用户可能把模型常识误认为已经过团队审核的知识。

troubleshooting 信号弱说明当前模块字段还需要面向任务类型扩展。`caveats` 字段本来可以承载常见错误、排障提示和适用条件，但测试材料显示某些模块的 `caveats` 为空，摘要也没有把 debugging 场景暴露出来。系统当前更适合解释流程和机制，不足以充分支撑排障类问答。

长文档处理仍然只是实现增强。分块、4k chunk cap、跨块去重、JSON retry 和原语言保留能降低部分抽取风险，但不能证明长文档抽取质量稳定。[证据不足：当前材料没有保存长文档输入、chunk 过程、输出模块质量、重复情况和人工质量判断。]

写路径证据弱于读路径。当前最强证据集中在 MCP 协议、索引读取、模块搜索和模块加载。虽然 release gate 中出现 `module_crud_http`，但 upload、create、复杂修改、search-after-write 和 load-after-write 还没有形成同等强度的端到端证据。

规模外推需要克制。`2026-06-13` release gate 覆盖的是 `xs/s/m`，没有充分证据支持 `l/xl` 规模。本文不能把小中规模下的 readiness 结果写成大规模知识平台能力。

多语料 judged baseline 缺失限制了比较结论。本文可以说结构化模块在工程治理上更利于保持边界、支持审核和按需加载，但不能说它在检索准确率上普遍强于 chunk-only retrieval。[证据不足：缺少统一 query set、BM25/关键词 chunk baseline、chunk-only retrieval baseline 和指标表。]

### 6. 讨论

Knowledge Manager 的主要价值在于把知识治理前移。传统检索系统更多关注“能不能召回相关文本”，而小中型团队知识库还需要回答“这条知识是否被确认、是否有边界、是否可追踪”。结构化模块、人工审核和 Git 存储共同处理的是后一个问题。

MCP 按需加载的意义在于让审核后的知识进入运行时上下文。客户端先读索引，再搜索和加载模块，这使知识访问行为更容易被观察和改进。MCP 本身不保证知识正确，也不替代权限、安全和质量控制。它提供的是连接路径，治理仍由系统和团队流程承担。

与 chunk-only retrieval 的关系应写成互补和取舍。Chunk-based retrieval 在大规模语义召回方面仍然重要，尤其当知识规模超过人工治理范围时，它可能更合适。Knowledge Manager 更适合可人工治理的小中型知识库，尤其是团队需要审查、追踪、复用和约束知识边界时。

人工审核带来的成本不能回避。`extract-review-approve` 会降低入库速度，也要求维护者投入判断。如果团队缺少维护人员，或者知识变化速度远高于审核能力，人工审核可能成为瓶颈。本文的主张并不是“人工审核总是更好”，而是“在需要责任边界的小中型团队知识库中，人工审核有明确工程价值”。

当前证据证明了系统链路和若干工程特性。MCP 协议路径已通过测试，`xs/s/m` release gate 达到项目门槛，搜索路径有明确时延，受控路由场景中观察到模块选择能力。这些结果支持 Knowledge Manager 作为应用型系统方案的可行性。

当前证据没有证明普适性能优势。没有多语料 judged baseline，就不能把“更利于治理”写成“检索性能更高”。没有长文档专项，就不能写“长文档问题已解决”。没有真实会话 traces，就不能写“全自动路由成熟”。没有完整写路径 E2E，就不能把写路径写成与读路径同等充分。

适用边界应收在可人工治理规模内。本文讨论的小中型团队知识库，更接近工程团队内部知识复用场景，而不是开放域问答、超大规模企业搜索或完全自动知识平台。这个范围不算大，但它与当前证据相匹配。

### 7. 引言

AI 协作开发改变了团队知识库的使用方式。过去，知识库主要给人查阅，开发者可以在阅读中自行判断内容是否过期、是否适用、是否存在遗漏。现在，知识还可能被代码代理检索、摘要、加载进上下文，并转化为代码修改建议或排障步骤。知识库因此不再只是文档集合，而逐渐成为人和模型共同使用的工程基础设施。

小中型团队知识库的难点不只是“找不到”。团队内部文档往往包含架构决策、接口约束、部署经验和 caveat，这些内容的价值依赖具体上下文。一个文本片段即使命中查询，也未必能说明它是不是当前版本仍可用，是否经过团队确认，或者是否只能在某个条件下使用。对 AI 协作开发来说，这类边界信息如果缺失，模型可能把局部文本当作通用规则。

RAG 和 chunk-based retrieval 为语言模型接入外部知识提供了成熟路线。它们适合处理大规模文本集合中的语义召回问题，也能作为 Knowledge Manager 后续对照评估的强 baseline。本文不否定这一路线。本文关注的是更窄的工程问题：在可人工治理的小中型团队知识库中，知识是否可以被组织成更容易审核、追踪和按需加载的模块。

Knowledge Manager 围绕这一问题设计。系统把知识抽取为结构化模块，保留 `overview`、`details`、`examples`、`references` 和 `caveats` 等字段；模块先进入 `.staging/`，经人工 review 和 approve 后入库；approved modules 以 Git 原生 JSON 文件保存；CLI 面向人工维护，MCP 面向 AI 客户端按需读取。

本文的贡献是一个应用型系统方案及其边界清楚的工程验证。系统设计层面，本文说明结构化模块、人工审核、Git 存储和 MCP 按需加载如何配合。实现层面，本文描述抽取、审核、索引、CLI/MCP 服务和长文档增强。验证层面，本文报告 MCP 协议测试、release gate、搜索时延、受控路由和评测框架能力，并把失败案例纳入结果解释。

本文不把当前结果解释为通用 RAG 结论。现有证据主要覆盖读路径、搜索路径和协议路径；长文档、写路径、真实会话路由和多语料 judged baseline 仍不足。本文更稳妥的定位是：Knowledge Manager 为小中型团队知识库提供了一条结构化、可审核、可追踪、可按需加载的工程路径。

### 8. 摘要

小中型团队知识库在 AI 协作开发中承担的不只是检索功能，还需要保留知识边界、审核记录和维护路径。仅依赖文本切块的检索组织方式便于接入 RAG 流程，但在团队知识复用场景中，chunk 是否经过确认、是否有 caveat、是否能按任务边界进入上下文，同样会影响系统可靠性。

本文围绕 Knowledge Manager 设计并实现了一种结构化知识模块管理与 MCP 按需加载系统。系统以包含 `overview`、`details`、`examples`、`references` 和 `caveats` 的知识模块为基本单元，采用 `extract-review-approve` 工作流控制知识入库，使用 Git 原生 JSON 存储支持审查与追踪，并通过 CLI 与 MCP 双接口提供知识访问。

当前可复核证据显示，Knowledge Manager 已形成从抽取、审核、批准到服务的工程链路。MCP 协议测试 `14/14` 通过；`2026-06-13` release gate 在 `xs/s/m` 三档均为 `ready_for_production=true`；`search_http` 与 `mcp_search_modules` 具备 mean 和 p95 时延记录；OAuth 知识库的 5 个受控路由场景中有 4 个完成正确模块选择。

本文将这些结果解释为小中型团队知识库场景下的工程可用性证据，而不是普遍性能优势证明。当前证据仍主要集中在读路径、搜索路径和协议路径；多语料 judged baseline、长文档专项、写路径 E2E 和真实会话路由仍需补充。基于现有材料，结构化、经审核并支持 MCP 按需加载的知识模块，更适合被理解为一种便于审查、追踪和复用的应用型系统方案。

### 9. 结论

Knowledge Manager 展示了一种面向小中型团队知识库的结构化知识管理路径。系统通过结构化模块保留知识边界，通过 `extract-review-approve` 工作流引入人工治理，通过 Git 原生 JSON 存储支持审查与追踪，并通过 CLI 与 MCP 双接口服务人类维护者和 AI 协作客户端。

现有验证支持系统具备基本工程可行性。MCP 协议测试 `14/14` 通过，`2026-06-13` release gate 在 `xs/s/m` 三档达到项目设定门槛，搜索路径有明确时延记录，受控路由测试显示结构化索引能在有限场景下支持模块选择。这些结果说明系统不是概念性设计，而是已经形成可运行链路。

本文的结论应保持克制。当前材料不能证明 Knowledge Manager 在检索性能上普遍强于 chunk-based RAG，也不能证明长文档、写路径、`l/xl` 规模或真实会话下的自主路由已经充分成熟。更稳妥的结论是：在可人工治理的小中型团队知识库中，结构化、经审核并支持 MCP 按需加载的知识模块，为 AI 协作开发提供了一条更便于审查、追踪和复用的工程路径。

后续工作应优先补齐证据链。多语料 judged baseline 对比可检验结构化模块相对于纯切块组织的收益与代价；metadata 与 `caveats` 消融可解释哪些字段真正改善路由和排障；长文档专项和写路径 E2E 可补齐当前最弱的工程证据。只有这些结果补齐后，本文的结论才适合进一步升级为更强的实证判断。
