# Knowledge Manager 论文初稿（A-G 结构版）

## A. 一句话核心论点

在小中型团队知识库场景中，本文通过 Knowledge Manager 所采用的结构化知识模块、`extract-review-approve` 工作流与 MCP 按需加载机制，实现了比 `chunk-only retrieval` 更清晰的语义边界、更可执行的人工治理与更可审查的知识复用路径，证据来自 README、MCP 协议测试 `14/14` 通过、`2026-06-13` 在 `xs/s/m` 三个规模上的 release gate 结果、路由测试 `4/5` 成功以及评测代码与测试中已实现的检索指标，其适用边界是当前证据主要覆盖读路径、搜索路径与协议路径，尚不能外推到所有 chunk-based RAG、`l/xl` 规模、充分验证的长文档场景和 live conversation 下的自主路由。

## E. 正文初稿

### 1. 系统设计

Knowledge Manager 的设计起点不是提升某个单一检索指标，而是处理小中型团队知识库在长期维护中的几个实际问题。团队知识往往不是一次性问答材料，而是会反复被开发者、维护者和代码代理读取、修订和交叉引用的工作资产。如果知识组织只依赖文本切块，片段虽然容易进入检索流程，但模块责任边界、人工审核位置和后续维护路径往往不够清楚。

本文采用的基本单位是结构化知识模块，而不是把 chunk 作为唯一组织单元。根据项目 README，单个模块至少包含 `overview`、`details`、`examples`、`references` 和 `caveats` 等字段。这种做法的直接目的，不是追求形式上的结构化，而是把“这条知识到底在讲什么、为什么这么做、有什么限制、和哪些模块相关”提前写进数据结构里。对团队知识库来说，这比把相关信息散落在多个 chunk 里更便于后续审查和复用。

系统在知识进入正式库之前保留了一个明确的人工审核阶段。Knowledge Manager 将原始文本先抽取到 `.staging/`，随后再由人工执行 review 和 approve。这个设计会增加 ingest 阶段的工作量，但它换来的是一个更稳定的治理边界。对于团队内部知识，很多内容并不是“语义上像就能用”，而是需要确认它是否符合当前实践、是否遗漏 caveat、是否可以被后续代理直接引用。本文把这一点视为系统设计的一部分，而不是流程中的附属操作。

系统在运行时采用 MCP 按需加载，而不是一次性把所有知识塞进上下文。README 给出的接口包括 `knowledge://index`、`load_module`、`search_modules` 和 `list_categories`。这意味着客户端可以先读索引，再按任务选择需要的模块。对于 AI 协作开发场景，这种设计的意义在于把“先定位、再加载”的行为前置到接口层，而不是完全交给下游提示词自己处理。从工程角度看，这样更容易控制上下文体积，也更方便分析加载行为。

Knowledge Manager 还把知识存储保持在 git 可管理的文件形态上。项目文档明确将其描述为 git-native JSON storage，并强调 approved module 可以直接 diff、review 和 version。这个选择并不新，但它与本文的主题高度相关。本文关注的是团队知识治理，而不是孤立的检索召回。如果知识模块能够沿用开发团队已经熟悉的代码审查和版本管理习惯，那么系统的引入成本会更低，知识变更也更容易追踪。

从这个角度看，Knowledge Manager 的核心主张不是“结构化一定比 chunk 更准”，而是“在小中型团队知识库里，结构化、可审查、带人工审核的模块组织方式更利于稳定使用”。这个主张目前主要建立在系统结构与已有验证结果之上，因此本文后面也会把适用边界写清楚，避免把它扩展成对所有 RAG 方案的普遍结论。

### 2. 实现细节

Knowledge Manager 的实现由存储、抽取、审核和服务四条链路组成，其中最关键的是模块如何从原始资料进入正式知识库。系统首先通过 CLI 读取原始文本，然后交给 extractor 生成结构化模块，生成结果先写入 `.staging/`，审核通过后再进入正式目录并更新 `index.json`。README 中给出的目录结构和命令序列，与这条实现路径是一致的。

抽取模块并不是简单地把输入一次性发给模型。`src/knowledge_manager/extractor.py` 中实现了 `_chunk_text`，用于把长文本切成多个片段处理；同时 `_effective_chunk_size()` 会把实际 chunk 大小限制在 `4000` 字符以内。这说明实现者已经意识到长输入在模型调用中的稳定性问题，因此用分块来降低单次抽取的风险。这里要强调的是，这只能说明系统对长文档做了工程增强，还不能据此宣称长文档问题已经被完全解决。

分块之后，系统还做了跨块去重。`extract()` 在遍历各 chunk 返回结果时维护 `seen_ids` 集合，对重复模块 ID 直接跳过。这一处理很实际，因为长文本切块后常见的问题不是完全抽不出来，而是不同 chunk 抽出部分重叠的模块。跨块去重不能保证抽取一定完整，但至少减少了知识库里出现同名重复模块的概率。

为提高模型输出的可解析性，extractor 还实现了 JSON 重试逻辑。`_call_llm_with_retry()` 在模型第一次返回的内容无法解析为 JSON 数组时，会把错误原因回写给模型，并要求它“只返回 JSON array”。如果第一次返回的是 JSON 对象而不是数组，也会再试一次。这个设计说明系统并没有把 LLM 输出视为天然可靠，而是做了必要的格式约束和恢复路径。对应用型系统来说，这类细节往往比空泛地写“采用大模型抽取”更重要。

抽取提示词还明确要求保留源文本原语言。README 和 `extractor.py` 的 prompt 都提到，如果源文本是中文，就输出中文标题和内容。这一点看起来像实现细节，其实和团队知识复用有关。对于中小团队知识库，知识往往天然是混合语言的，如果系统强行统一改写，很容易丢失原有语境。当前实现至少在提示层面对这个问题做了保留。

在服务侧，Knowledge Manager 通过 CLI 与 MCP 双接口暴露知识。`src/knowledge_manager/cli.py` 中可以看到 `list`、`search`、`show`、`review`、`serve` 等命令，README 则进一步给出了 `knowledge://index`、`load_module`、`search_modules` 和 `list_categories()` 这几类 MCP 能力。这样一来，人可以通过 CLI 维护和检查知识库，代理或编辑器客户端则可以通过 MCP 查询和加载模块。两条接口面向的使用者不同，但访问的知识对象是一致的，这减少了维护两套知识视图的成本。

实现中还有一个值得保留的点是审查友好的文件形态。系统使用 JSON 模块文件和自动维护的 `index.json`，并把 `.staging/` 作为待审核区。相比把知识放进难以审查的二进制索引或仅在运行期构造的缓存里，这种做法更容易追踪知识从“原始材料”到“正式模块”的变化路径。对于团队协作型知识库，这种可见性本身就是系统价值的一部分。

### 3. 实验设置

本文不把 Knowledge Manager 的现有材料包装成一次完整的大型 benchmark，而是把它们视为一组分层证据。第一类证据是协议与接口层验证，主要来自 `test-results/mcp-protocol.md`。第二类证据是生产门禁与性能结果，主要来自 `test-results/perf-run-production-gate-20260613-r16-matrix-summary.json`。第三类证据是路由行为测试，主要来自 `test-results/llm-routing.md`。第四类证据是评测框架能力本身，来自 `src/knowledge_manager/eval_runner.py`、`src/knowledge_manager/retrieval_eval.py` 及其测试文件。

协议层测试使用了真实 OAuth 知识库，并按照 MCP `2024-11-05` 规范检查握手、资源发现、资源读取、工具列表、工具调用和错误处理。`test-results/mcp-protocol.md` 显示总测试数为 `14`，通过数也是 `14`。这类证据不能直接说明“知识组织方式更优”，但可以说明 MCP 服务路径不是纸面设计，而是已经跑通过的实际接口。

生产门禁证据来自 `2026-06-13` 的 matrix summary。当前可以直接引用的三档规模是 `xs`、`s` 和 `m`，三档的 `ready_for_production` 都为 `true`。同时，该文件还给出了 `search_http` 与 `mcp_search_modules` 的 mean 和 p95 延迟：`search_http` 在 `xs/s/m` 上分别约为 `207/220 ms`、`371/381 ms`、`405/414 ms`；`mcp_search_modules` 分别约为 `208/230 ms`、`477/487 ms`、`594/625 ms`。这些数据适合作为工程可用性的证据，但它们仍然是特定规模下的 release gate 结果。

路由行为测试来自 `test-results/llm-routing.md`。该测试基于一个真实 OAuth 2.0 知识库，共设计了 `5` 个场景。报告显示其中 `4` 个场景的模块选择是正确的，同时所有测试里没有出现明显的 irrelevant over-loading。这说明“先读索引、再按需加载模块”这个思路在受控场景下是可用的。不过，场景数仍然很少，因此本文只把它写成“有界证据”。

评测框架方面，`src/knowledge_manager/retrieval_eval.py` 已实现 `first_hit_rank`、`MRR`、`nDCG@k` 和 `recall@k`，`src/knowledge_manager/eval_runner.py` 则在此基础上进一步汇总 `baseline_win_rate`、`false_positive_rate`、`false_negative_rate`、`policy_failure_rate` 和 `retrieval_failure_rate`。相应测试也覆盖了这些字段的计算与输出。这一部分能说明项目具备更正式的评价基础，不再只停留在命中率演示；但它仍然不等于“已经完成了充分的 baseline 对比实验”。

本文还需要明确哪些不属于现阶段实验设置。首先，当前没有多个真实语料上的 judged query 对比。其次，虽然代码支持 baseline 字段和失败分解，但现有测试并不足以证明这些机制已经在复杂失败样例上被充分验证。再次，长文档处理和写路径虽然有一定实现与门禁信息，但整体证据链明显弱于协议、搜索和读路径。

因此，本节的实验设置是“现有可复核证据的整理”，而不是“新增完整实验”。这种写法比较克制，但和当前材料状态是一致的。

### 4. 结果分析

协议结果先回答了一个很基础但很关键的问题：Knowledge Manager 的 MCP 路径是否可用。`test-results/mcp-protocol.md` 中的 `14/14` 通过，覆盖了初始化握手、资源列表、索引读取、工具列表、模块搜索、模块加载、分类列表和错误处理。对应用型系统论文来说，这类结果虽然不华丽，但它说明系统的外部服务接口已经达到可以稳定接入客户端的程度。

发布门禁结果主要说明系统在既定规模内具备工程可运行性。`2026-06-13` 的 matrix summary 中，`xs`、`s`、`m` 三档全部给出 `ready_for_production = true`。如果只看搜索相关路径，`search_http` 和 `mcp_search_modules` 都通过了门槛，而且实际延迟明显低于目标阈值。这类结果不能被解释成“系统在更大规模上同样成立”，但至少说明本文讨论的方案不是停留在离线脚本层面，而已经有了稳定的服务化形态。

路由结果支持的是“按需加载有用”，而不是“自主路由已经成熟”。`test-results/llm-routing.md` 显示 5 个场景中有 4 个场景模块选择正确，且没有无关模块过度加载。这一点与结构化模块和索引摘要的设计是相符的，因为模块标题、摘要和标签确实给了模型比较明确的检索线索。不过同一份报告也指出，细粒度模块会导致某些查询需要加载 `3-6` 个模块，说明模块边界清晰并不自动等于加载开销低。

从当前证据看，Knowledge Manager 更强的不是“搜索分数”，而是“工程适配性”。一方面，知识以 JSON 模块形式进入 git，可以被 diff 和审查；另一方面，客户端并不需要在运行时整库注入，而是可以先查索引再读模块。对于小中型团队知识库，这种组合方式确实更符合长期维护需求。本文愿意写到这一步，但不会把它直接升格为“全面优于 chunk-only RAG”，因为现有材料里缺少多个真实语料与 judged baseline 的正式比较。

评测框架的结果也值得单独解释。`eval_runner.py` 和 `retrieval_eval.py` 说明项目已经具备从 hit/miss 进一步走向 rank-based evaluation 的能力，这比只报命中率更扎实。同时，代码里还加入了 `policy_failure_rate` 与 `retrieval_failure_rate` 的划分，表明作者已经意识到失败不只来自检索本身，也可能来自策略过滤或任务约束。问题在于，现有测试更像是“功能存在性验证”，还不足以支撑更强的实验结论。因此本文会把这部分写成“评测能力已经具备”，而不是“失败分解已经被完整实验验证”。

结果里也已经能看到几类不应回避的弱点。首先，路由测试中的 OAuth/JWT 场景表明系统还不能稳定识别知识边界之外的问题。其次，redirect troubleshooting 场景说明当前模块摘要和 `caveats` 字段对排障信息的支持偏弱。再次，长文档相关证据目前主要来自 extractor 的实现增强，而不是专项实验结果，因此还只能算“风险有所下降”，不能算“问题已经解决”。最后，尽管 release gate 中包含 `module_crud_http`，但整体证据仍明显偏向读路径、搜索路径和协议路径，写路径暂时没有形成同等强度的论文叙事。

总的来看，当前结果支持这样一个较稳妥的判断：Knowledge Manager 在小中型团队知识库条件下，已经展示出较好的协议可用性、发布可运行性、按需加载能力和后续评测扩展性。这足以支撑一篇应用型系统论文的主体论证，但还不足以支撑算法优越性或大规模普适性结论。

### 5. 失败案例与局限性

知识边界识别不足是当前最明确的失败点之一。`test-results/llm-routing.md` 中的 “OAuth 和 JWT 有什么区别？” 场景被设计成边界测试。该知识库只覆盖 OAuth，但不覆盖 JWT。报告显示模型最后仍可能加载 `oauth-2-0-framework`，并依赖自身常识去补全 JWT 对比，而没有明确停在“JWT 不在知识库中”。这说明系统目前缺少足够强的 out-of-scope 信号。

troubleshooting 信号偏弱也是一个实际问题。`test-results/llm-routing.md` 在 “如何调试 OAuth 重定向问题？” 场景里指出，虽然模型能加载与 redirect 机制相关的模块，但模块摘要并没有明显暴露 debugging 信息，而且 `caveats` 字段还是空的。换句话说，系统目前对“怎么工作”类知识的支持强于对“出问题时怎么查”类知识的支持。这种差异在应用型系统里很常见，论文里不应该回避。

长文档处理已经做过增强，但风险仍在。`src/knowledge_manager/extractor.py` 中的分块、`4000` 字符上限、跨块去重和 JSON retry 都说明实现层面比早期版本更稳。但这些实现细节并不能自动转化成“长文档稳健性已被充分验证”。如果没有专门的长文档 benchmark 和留存输出，本文最多只能说系统对长文档问题做了针对性修补。

短查询与缩略词检索也暴露出弱点。`test-results/retrieval-accuracy.md` 记录了一个很典型的失败案例：查询 `auth` 时，尽管所有模块都处于 `auth` 类别，系统仍返回空结果。这一现象说明当前的匹配机制对短词、词干和缩略表达的支持还不稳定。它不一定会影响所有团队知识库，但至少提示我们不能把现有搜索能力写得过满。

写路径证据也弱于读路径。当前最强的一组结果仍然集中在协议测试、索引读取、搜索延迟和路由加载上。虽然 release gate 文件中出现了 `module_crud_http` 并且三档都通过，但论文层面的证据尚未形成一条和读路径同样完整的叙事链。尤其是 upload、create、复杂修改这类操作，目前没有对应的、可直接写进结果部分的强验证材料。

评测指标本身也有边界。现有代码确实实现了 `false_positive_rate` 和 `false_negative_rate`，但它们是 case 级启发式定义，不是标准 IR 混淆矩阵意义下的 FP/FN。`policy_failure_rate` 和 `retrieval_failure_rate` 也是如此，当前更像失败归因的工程近似，而不是严格因果分解。这一点如果不说明，很容易在审稿时被抓住。

这些失败点放在一起，反而更能说明本文的定位应该收在“小中型团队知识库的应用型系统方案”。如果把它写成算法论文，上述问题会显得很刺眼；但如果把它写成工程实现与验证型工作，这些局限恰恰构成了真实的边界说明。

### 6. 讨论

#### 6.1 结果意味着什么

当前证据更支持一种工程判断，而不是一种理论判断。Knowledge Manager 把知识组织、人工审核、模块存储和运行时加载放在同一条链上，形成了从原始资料到运行期使用的闭环。这个闭环的价值主要体现在治理和维护上，而不是证明某种检索算法本身更先进。

对于小中型团队来说，知识库常见的问题并不是“完全找不到相关内容”，而是“找到的内容边界不清、很难确认是否可直接复用、变更后缺乏追踪”。结构化模块和 git-native 存储正好对准了这类问题。人工审核虽然牺牲了一部分自动化速度，但换来了知识入库前的最后一道质量控制。MCP 按需加载则让这些经过审核的模块可以在运行期按需进入上下文，而不是整库展开。

#### 6.2 为什么不是把 chunk-only 彻底否定掉

本文并不否认 chunk-only retrieval 的价值。README 自己也把 classic RAG 的优点写得比较清楚，即它在更大规模上通常有更强的语义召回能力。本文真正想指出的是，在小中型团队知识库里，知识单元不仅承担“被搜到”的任务，还承担“被审查、被复用、被维护、被解释”的任务。单纯的 chunk 组织在这些方面未必总是最省事。

因此，本文更合适的表述不是“Knowledge Manager 优于 chunk-only retrieval”，而是“在当前证据下，Knowledge Manager 这种结构化、带人工审核并支持 MCP 按需加载的方案，在小中型团队知识库里显示出更好的工程适配性”。这种说法更克制，也更符合现有证据的强度。

#### 6.3 适用边界

本文的适用边界需要明确写出来。第一，现有最强证据集中在 `xs/s/m` 规模，不能外推到 `l/xl`。第二，当前最稳的是读路径、搜索路径和协议路径，写路径证据相对弱。第三，长文档处理虽已增强，但还不能说被充分验证。第四，live conversation 条件下的自主路由仍只有小样本案例。第五，本文没有完成多语料、多人标注或 judged baseline 级别的正式对比，因此不能把工程上的“更适合”写成普遍意义上的“更优”。

如果把这些边界接受下来，Knowledge Manager 其实已经具备一篇应用型系统论文需要的基本完整度。它回答的是一个具体场景里的系统设计问题，而不是一个试图通吃所有知识检索路线的宏大问题。

### 7. 引言

团队知识库正在从“给人看的文档集合”变成“同时给人和代码代理使用的工作基础设施”。在这种变化下，知识是否可检索当然重要，但知识是否容易审查、是否能保持语义边界、是否能在多次修改后继续被可靠复用，同样重要。对很多小中型团队来说，后面这些问题往往更早成为系统使用中的摩擦点。

现有基于文本切块的检索方式为知识注入提供了一个直接入口，但它并不总能保留知识的责任边界。一个 chunk 可以命中问题，却不一定能说明这段内容在团队实践中属于什么决策、适用于什么条件、有什么 caveat，或者是否已经过人工确认。随着知识库逐渐变成协作资产，这些问题会越来越突出。

Knowledge Manager 试图处理的，正是这种“可用但不易治理”的状态。它没有把 chunk 当作唯一知识单元，而是把知识组织成结构化模块；它没有把抽取结果直接写入正式库，而是保留 `extract-review-approve` 审核流程；它也没有要求客户端一次性读入全部内容，而是通过 MCP 暴露索引和模块访问能力，使加载行为可以按任务展开。这样的设计更偏工程治理，而不是算法创新。

本文的重点不是证明 Knowledge Manager 在所有条件下都优于现有 RAG 系统，也不是提出新的理论检索方法。本文关心的是，在小中型团队知识库场景中，结构化、经人工审核的知识模块结合 MCP 按需加载，是否能形成一条更容易维护、更便于审查、也更适合 AI 协作开发的知识使用路径。

从当前材料看，这个问题已经有了一些可以复核的证据。Knowledge Manager 的 MCP 协议测试 `14/14` 通过，`2026-06-13` 的 release gate 在 `xs/s/m` 三个规模上给出 `ready_for_production = true`，路由测试在真实 OAuth 知识库上取得了 `4/5` 的正确模块选择结果，同时评测代码已经支持 rank-based 指标和失败类型分解。这些结果不足以证明普适优势，但足以支持一篇有边界意识的应用型系统论文。

因此，本文把自己的结论收在一个较小但更稳的范围内：对于小中型团队知识库，Knowledge Manager 所采用的结构化模块、人工审核和 MCP 按需加载机制，显示出比单纯 chunk 组织更好的工程适配性；与此同时，它在大规模、长文档、写路径和 live routing 场景下仍有明显边界。

### 8. 摘要

面向 AI 协作开发的团队知识库，不仅需要可检索，还需要可审查、可维护和可复用。仅以文本切块作为知识组织单位的方案，虽然便于接入检索流程，但在语义边界保持、人工治理和长期维护上往往存在额外成本。针对这一问题，本文围绕 Knowledge Manager 这一应用型系统，设计并实现了结构化知识模块、`extract-review-approve` 工作流、git-native JSON 存储以及基于 MCP 的按需加载机制，使知识既能被人工审核和版本化管理，也能在运行时由客户端按任务选择性读取。

当前可复核证据表明，该系统已经形成较完整的工程实现链路。MCP 协议测试在 `2026-05-29` 的报告中取得 `14/14` 通过；`2026-06-13` 的 release gate 在 `xs`、`s` 和 `m` 三个规模上均给出 `ready_for_production = true`；同一批结果还提供了 `search_http` 与 `mcp_search_modules` 的时延数据。基于真实 OAuth 知识库的路由测试显示，5 个场景中有 4 个场景完成了正确的模块选择，且未出现明显的无关过载。与此同时，系统评测代码已支持 `first-hit rank`、`MRR`、`nDCG@k`、`recall@k`、`baseline win rate` 以及基于失败类型的工程性分解。

这些结果说明，结构化、经人工审核的知识模块结合 MCP 按需加载，在小中型团队知识库中具有较好的工程适配性，尤其适合需要人工治理、版本审查和稳定知识复用的场景。不过，本文也明确保留边界：当前证据仍以读路径、搜索路径和协议路径为主，尚不能证明其全面优于所有 chunk-based RAG，也不能外推到 `l/xl` 规模、充分验证的长文档场景或 live conversation 下的自主路由。

### 9. 结论

本文围绕 Knowledge Manager 讨论了一种面向小中型团队知识库的应用型系统方案。与把文本 chunk 作为主要知识单元的组织方式相比，该系统更强调结构化模块、人工审核、git-native 存储和 MCP 按需加载之间的配合。就当前证据而言，这一方案已经表现出较好的工程可用性和治理可见性。

现有材料能够较稳地支持几项结论。第一，Knowledge Manager 已经形成了从抽取、审核到服务的完整实现链路，而不是停留在概念层。第二，MCP 接口与发布门禁结果说明系统在 `xs/s/m` 范围内具备可运行性。第三，路由测试和评测框架显示，这套方案不仅能被接入，还具备继续做正式评价的基础。对于小中型团队知识库，这些结果足以说明结构化、经人工审核的模块组织方式具有现实意义。

同时，本文的结论必须收在当前证据之内。我们不能据此宣称系统全面优于所有 chunk-based RAG，也不能把现有结果外推到更大规模、长文档稳健性、写路径完整能力或 live conversation 下的自主路由。更合适的表达是：在当前材料所覆盖的范围内，Knowledge Manager 展示出一种更便于团队治理和 AI 协作复用的知识组织与服务路径。这个结论不大，但比较稳。
