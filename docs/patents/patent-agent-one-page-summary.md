# Knowledge Manager 专利代理人整合说明

> 用途：给专利代理人快速了解项目、公开风险、已有申请初稿和建议专利布局。本文为技术交底摘要，不构成正式法律意见。

## 一、项目是什么

Knowledge Manager 是一个面向 AI 编程智能体、大语言模型上下文加载和团队知识治理的知识管理系统。它把非结构化或半结构化资料（例如产品文档、运行手册、事故复盘、架构说明、Confluence、Notion、Markdown 文件等）转化为可审查、可版本化、可检索、可通过 MCP 加载的结构化知识模块。

它和普通 RAG 系统的差异主要在于：

1. 不是把文档简单切成 chunk，而是生成带有 `overview`、`details`、`examples`、`references`、`caveats` 等字段的结构化知识模块。
2. 知识以 Git 原生 JSON 文件和索引保存，可 diff、可 review、可版本化。
3. 面向智能体运行时按需加载知识，而不是只做普通问答。
4. 有外部源同步、来源追踪、审核、检索策略、失效治理和运维视图等治理能力。

典型流程是：

```text
外部源文档 / 本地资料
  -> LLM 抽取结构化知识模块
  -> staging 暂存
  -> 人工 review / approve
  -> 写入 Git 原生知识库
  -> CLI / HTTP / MCP 提供检索和模块加载
```

### A1：源片段映射、影响范围判定与分级失效控制

建议发明名称：

一种基于源片段映射的派生知识模块影响范围判定与分级失效控制方法、装置、电子设备及存储介质。

核心问题：

外部源文档发生局部变化时，如何精确判断哪些派生知识模块、哪些模块字段受到影响，并根据影响程度控制失效状态、检索可见性和局部重抽取。

核心方案：

1. 将外部源文档解析为多个源片段。
2. 在知识抽取时建立 `source_document -> source_span -> module_id -> module_section` 的映射关系。
3. 源文档更新后，基于版本、checksum、标题路径、字符范围、内容摘要等确定源片段变更集合。
4. 根据映射关系把源片段变更传播到派生知识模块和模块字段。
5. 依据变更比例、字段类型、模块置信度、访问频次、任务风险等级等确定分级失效状态。
6. 根据分级失效状态控制检索可见性、排序权重、提示状态、抑制召回或局部重抽取。

建议强调：

1. 字段级影响传播，不是文档级或模块级粗粒度 stale。
2. 源片段变化到模块字段的多级映射。
3. 失效等级与检索可见性、审核、重抽取联动。
4. 局部重抽取，而不是全量重建。

建议避免：

1. 仅主张“记录 provenance”。
2. 仅主张“源变化后标记 stale”。
3. 仅主张“展示 source/module view”。

### A2：溯源置信度、检索抑制与自动重抽取

建议发明名称：

一种基于溯源置信度的知识模块检索抑制与自动重抽取触发方法、装置、电子设备及存储介质。

核心问题：

知识检索阶段如何不仅根据相关性召回模块，还根据模块当前可信程度决定正常召回、降权召回、提示召回、抑制召回或触发重抽取。

核心方案：

1. 接收知识检索请求并生成候选知识模块集合。
2. 获取候选模块的溯源元数据，例如源版本、checksum、源片段覆盖率、抽取时间、审核状态、失效状态、模块置信度和历史使用反馈。
3. 根据溯源元数据计算溯源置信度分值。
4. 根据查询任务类型或风险等级确定动态置信度阈值。
5. 根据置信度分值和阈值控制召回状态。
6. 当候选模块满足重抽取触发条件时，根据源文档或源片段生成重抽取任务。
7. 重抽取结果进入暂存区或审核队列，审核通过后更新知识模块、索引和搜索投影。

建议强调：

1. 连续溯源置信度评分，不是简单 status/stale 过滤。
2. 相关性得分与溯源置信度联合排序。
3. 高风险任务使用更高可信度阈值。
4. 低可信候选触发局部重抽取。
5. 召回控制原因码用于审计和策略优化。

建议避免：

1. 仅主张“根据状态过滤搜索结果”。
2. 仅主张“风险等级影响检索策略”。
3. 仅主张“低质量结果重新抽取”。

## 四、建议的五个窄改进点

如果预算允许，可以考虑从 A1/A2 中拆出五个窄保护点。具体是否独立申请、同日提交、作为母案从属权利要求或后续分案，请代理人结合检索结果判断。

1. 字段级影响传播矩阵  
技术问题：源文档局部变化后，如何精确定位受影响模块字段。  
主句方向：建立源片段与派生知识模块字段之间的映射矩阵；响应于源片段变化，根据映射矩阵确定受影响字段集合；根据变化范围和字段类型计算影响值；根据影响值更新检索状态。

2. 分级 stale 状态机与检索可见性联动  
技术问题：布尔 stale 无法区分轻微过期、需要审核、禁止召回、正在重抽取和已恢复。  
主句方向：配置分级失效状态机；根据源片段变更、审核结果或重抽取结果触发状态迁移；根据迁移后的状态确定召回、降权、提示或抑制策略。

3. 溯源置信度评分模型  
技术问题：检索系统只看相关性，无法判断高度相关模块当前是否可信。  
主句方向：获取候选知识模块的溯源元数据；分别确定版本一致性得分、校验一致性得分、源片段覆盖率得分、新鲜度得分和审核得分；加权计算溯源置信度分值。

4. 高风险任务动态阈值召回控制  
技术问题：同一模块在普通查询可召回，但在部署、权限、安全、事故处理等高风险任务中可能不应召回。  
主句方向：识别检索请求对应的任务风险等级；根据风险等级确定溯源置信度阈值；将候选模块置信度与阈值比较；根据比较结果确定召回状态。

5. 低可信候选自动重抽取闭环  
技术问题：检索阶段发现低可信模块时，传统系统通常只过滤或提示，不能自动修复并回写索引。  
主句方向：在检索阶段确定低可信候选知识模块；根据关联源片段和模块字段生成重抽取任务；审核通过后更新模块内容及检索索引。

其中最建议优先保护的三个点是：

1. 字段级影响传播矩阵。
2. 溯源置信度评分模型。
3. 低可信候选自动重抽取闭环。

## 五、建议申请策略

建议代理人优先判断：

1. A1 和 A2 是否适合作为两个母案同日提交。
2. 五个窄点是否适合分别独立申请，还是并入 A1/A2 的从属权利要求。
3. GitHub 曾公开对宽权利要求新颖性的影响。
4. 哪些技术特征属于公开基线，哪些属于未充分公开的窄改进。
5. 是否需要补充实验数据，例如误召回下降率、重抽取任务减少比例、低可信模块抑制率、高风险任务召回准确率等。

个人建议：

1. 若预算有限，先做 A1/A2 两件母案，并在说明书中充分覆盖五个窄点。
2. 若预算充足，优先独立拆出“字段级影响传播矩阵”“溯源置信度评分模型”“低可信候选自动重抽取闭环”三件。
3. “分级 stale 状态机”和“高风险任务动态阈值”可以视检索结果决定独立申请或并入母案从属权利要求。

## 七、一句话概括

Knowledge Manager 不是单纯的知识库或普通 RAG 工具，而是面向智能体和大语言模型上下文加载的结构化知识治理系统。已公开基线可能包括知识模块化、MCP 加载、provenance、stale 和 routing policy；建议专利重点转向未充分公开的窄改进：字段级影响传播、分级失效状态机、溯源置信度评分、风险动态阈值召回控制、低可信候选自动重抽取闭环。
