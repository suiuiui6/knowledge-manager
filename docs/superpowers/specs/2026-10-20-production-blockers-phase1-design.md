# 第一阶段生产阻断项改进设计

## 目标

针对 `knowledge-manager` 当前单节点产品，关闭生产切换前最关键的安全、数据完整性、任务一致性和性能阻断项。设计保持文件型 Git 原生架构，不引入 Neo4j、Celery、LangGraph 或其他新的核心基础设施。

## 范围

本阶段包含四个批次：

1. 认证依赖与生产模式安全边界；
2. 索引完整性、漂移修复和关键文件原子写入；
3. ingestion job 的领取、租约、恢复和重复执行保护；
4. 搜索、推荐、管理面板和 MCP 搜索性能热点。

本阶段不包含 SaaS 计费、高可用多实例、GraphRAG 图数据库、全量向量检索或前端重做。

## 批次一：认证与租户安全

补齐 OIDC 运行时依赖并更新锁文件。生产模式在认证未配置、认证提供方不受支持或 token 验证失败时必须拒绝受保护请求，并保持健康检查与 readiness 的边界清晰。

租户范围从认证主体 claims 解析，普通用户不能通过 query/body 覆盖自己的 tenant 或 workspace。企业模式默认不把无 tenant 的共享模块暴露给所有租户，只有明确配置时才允许全局读取。HTTP、MCP、模块详情、搜索、任务和管理接口使用同一授权语义。

新增回归测试覆盖：缺失认证、无效 token、权限不足、跨租户模块读取、跨租户搜索、MCP 读取和管理员显式覆盖。

## 批次二：完整性与原子写入

把模块文件、`index.json`、搜索投影和推荐索引视为同一知识库快照。修改或删除模块后，派生状态必须通过现有失效/重建流程更新；完整性检查必须能发现 dangling、missing 和 drift，并提供可重复的修复命令。

任务状态、RBAC 配置和新增派生文件使用临时文件加 `os.replace` 的原子写入方式。对当前架构无法提供跨进程事务的操作，明确限制为单节点单 worker，并在运行手册中记录边界。

新增测试覆盖中断写入、索引漂移检测、重建后恢复、删除后搜索不可见以及重复修复幂等性。

## 批次三：任务一致性

`claim_ingestion_job` 只能领取 queued 或已过期 running 任务；有效租约期间禁止第二个 worker 重复领取。领取时写入 worker、attempt、heartbeat 和 lease，状态转换必须可观测。

保留本地文件队列和现有 worker。增加重复领取、过期租约恢复、失败后重试、未知 payload、结果写入失败和恢复后继续执行测试。任务成功必须在 staging 结果和必要派生状态完成后标记。

## 批次四：性能热点

先使用现有 benchmark harness 和 profiling 证据定位重复 I/O、重复重建、全量扫描及 JSON 序列化热点，再做最小修改。优先复用已生成的 search projection、recommendation index 和 materialized views，避免每个请求重复加载全部模块。

性能验收至少覆盖 XS、S、M 三个规模，并保留 `gate_summary` 与 `release_verdict`。不得用 XS 通过推断 S/M 通过；任何修复都要确认没有造成完整性、租户隔离或写路径回归。

## 验收标准

- `poetry.lock` 包含所有运行时导入依赖，干净安装冒烟通过；
- 认证、RBAC 和租户隔离回归测试通过；
- 完整性检查在正常库中通过，并能发现和修复人为制造的索引漂移；
- 任务重复领取和过期租约恢复测试通过；
- 适用的 pytest、black、mypy 检查通过；
- 新生成的 XS/S/M 矩阵报告包含完整 gate summary 和 release verdict；
- 只有 XS、S、M 全部通过且 readiness、integrity、部署和备份证据齐全，才允许称为生产阻断项已关闭。

## 风险与回滚

文件型并发控制无法等同于数据库事务。若测试发现多实例写冲突，保持单节点单 worker 约束，不通过放宽测试或隐藏失败来宣称支持多实例。每个批次保留独立提交和验证记录，性能退化或租户泄露时回滚对应批次并重新运行完整门禁。
